# 4회차 제출 — 박준우

> 계정: `cc02` · 작성일: 2026-11-16 · **받은 신고: B**

**결론:** net01의 DHCP 네임스페이스 `qdhcp-714d758c-…`의 iptables `INPUT` 맨 앞에 `169.254.169.254:80/tcp`를 버리는 DROP 규칙(`study-w4b-cc02`)이 들어가 있다. 그래서 메타데이터 요청이 haproxy에 닿기 전에 버려지고, 새로 부팅한 vm4가 공개키를 못 받아 키 로그인만 실패한다.

```
vm4 eth0 ─(169.254.169.254 via 10.102.0.2)─▶ … ─▶ net01 [qdhcp] tap473bdc44-0d ✓ 도착 ─▶ iptables INPUT #1 DROP ✂ ─▶ haproxy :80 (LISTEN, 대기 중)
DHCP(udp 67/68)·ICMP·SSH(22)는 이 규칙과 무관 → IP·ping·비밀번호 로그인은 정상
```

## 1. 읽기 핵심 (한 장)

- **포트의 IP는 누가 언제 정하나:** VM이 DHCP로 받기 전에, 포트를 만드는 순간 Neutron(IPAM)이 allocation pool에서 골라 DB에 적는다. DHCP 에이전트가 그 MAC→IP를 dnsmasq에 넘기고, dnsmasq는 그대로 나눠줄 뿐이다. 이번에도 vm4 포트 `10.102.0.172`가 `openstack port list`에 있었고, dnsmasq는 그 값 그대로 `DHCPACK`을 줬다.
- **메타데이터로 가는 두 길 (책 p.141·p.160):** 라우터가 있는 서브넷은 VM이 기본 게이트웨이(qrouter)로 요청을 보내고, qrouter가 프록시로 넘긴다. 라우터가 없는(isolated) 서브넷은 DHCP가 `169.254.169.254/32 via <DHCP 포트 IP>` host route를 내려줘서, qdhcp 네임스페이스의 프록시가 받는다.
- **우리 환경과 책의 차이:** `force_metadata = true`라서 **라우터가 있어도** DHCP가 host route를 내려준다. vm1·vm4 모두 `169.254.169.254 via 10.102.0.2`가 있고, /32라서 기본 경로(10.102.0.1)보다 우선한다. 즉 요청은 qrouter가 아니라 **qdhcp**로 간다. 프록시 프로세스도 책의 `neutron-ns-metadata-proxy`가 아니라 **`haproxy`**(`-f …/ns-metadata-proxy/<네트워크ID>.conf`)다. 책의 `neutron` CLI도 우리 환경에서는 `openstack` CLI다.
- **MTU 1450:** 물리 MTU 1500에서 VXLAN(IPv4) 오버헤드 50바이트를 뺀 값이다. VM에는 DHCP option 26으로 전달된다. 이번 신고 B와는 관계가 없어서 기각 목록에만 남겼다.
- **SRE 12장 "부정적 결과는 마법이다":** 이번 원인은 기각을 차례로 쌓아서 찾았다. "키가 다르다", "DHCP가 안 된다", "라우터로 간다", "haproxy가 죽었다", "요청이 안 온다"를 하나씩 기각하고 나니, "도착했는데 사이에서 버려진다"만 남았다.
- **SRE 6장 Black-box vs White-box:** Grafana 프로브는 기존 VM에 작은 ICMP만 보낸다. 메타데이터(tcp/80, 그것도 새로 부팅할 때만)는 프로브가 지나가지 않는 길이라 전부 초록일 수밖에 없다.

## 4. 원인 · 복구 방안

복구는 **실행하지 않았다.**

- **원인 (한 문장):** net01의 `qdhcp-714d758c-…` 네임스페이스 iptables `INPUT` 체인 맨 앞에 `169.254.169.254:80/tcp`를 버리는 DROP 규칙(`study-w4b-cc02`)이 끼어 있어서, 메타데이터 요청이 haproxy에 닿지 못한다.
- **요청이 마지막으로 확인된 지점 / 처음 사라진 지점:** qdhcp의 `tap473bdc44-0d`까지는 도착했다(tcpdump SYN 14개). 그 직후 iptables INPUT #1에서 사라졌다(카운터 +14, 도착한 SYN 수와 같음). haproxy는 그 뒤에서 `:80`을 듣고 있었으니, 요청이 haproxy까지 가지 못한 것으로 판단한다 (haproxy 로그는 직접 보지 않았다).
- **끊긴 지점이 이 증상으로 보인 이유 (미끼 설명):**
  - **IP·ping은 정상:** 규칙은 `tcp/80 → 169.254.169.254`만 막는다. DHCP(udp 67/68), ICMP, SSH(22)는 그대로 통과해서 "네트워크는 정상"으로 보였다.
  - **비밀번호는 되고 키만 실패:** cirros 비밀번호는 이미지에 들어 있는 기본값이라 메타데이터와 상관없다. 공개키만 부팅할 때 메타데이터 `public-keys`로 받아서 넣는다.
  - **기존 VM은 정상:** 지금 vm1도 메타데이터는 30/30 실패한다. 그런데도 키 로그인이 되는 것은, 규칙이 들어가기 전 부팅(vm1 생성 10/26)에서 받은 키가 디스크에 남아 있기 때문으로 **추정**한다. 키를 다시 받을 일이 없으니 드러나지 않는다. vm4(생성 11/10)는 규칙이 들어간 뒤 부팅해서 키를 한 번도 못 받은 것으로 보인다. 규칙이 들어간 시각은 확인하지 못했다.
  - **"요청 실패"가 바로 오지 않고 49초씩 걸림:** DROP은 응답(RST)을 안 보낸다. vm4 자신의 요청을 캡처하지는 않았지만, 49초 간격은 timeout까지 기다리는 모양과 맞고, vm1 캡처에서도 RST가 0개였다. REJECT였거나 haproxy가 죽어 있었다면 바로 실패했을 것이다.
- **복구하려면 (원인만 되돌리는 방법):** net01에서 끼어든 규칙 하나만, 규칙 내용을 그대로 지정해서 삭제한다.
  ```bash
  sudo ip netns exec qdhcp-714d758c-c0c0-408e-9499-caf0f74b1998 \
    iptables -D INPUT -d 169.254.169.254/32 -p tcp -m tcp --dport 80 \
      -m comment --comment study-w4b-cc02 -j DROP
  ```
  - 번호(`-D INPUT 1`)가 아니라 내용으로 지정해야, 그사이 순서가 바뀌어도 Neutron 규칙(`neutron-dhcp-age-INPUT` 점프)을 잘못 지우지 않는다.
  - dnsmasq, haproxy, DHCP 에이전트, `neutron-dhcp-age-*` 체인은 정상이므로 건드리지 않는다. 에이전트 재시작은 net01의 다른 네트워크에도 영향을 주고, 이 규칙은 Neutron이 관리하는 체인 밖에 있어서 재시작으로 지워진다는 보장도 없다 (추정).
  - 그다음 `openstack server reboot cc02-vm4`로 vm4가 부팅하면서 메타데이터(키)를 다시 받게 한다.
- **복구 후 무엇으로 확인하면 되는지:**
  - qdhcp `iptables -L INPUT -n -v`에 DROP 규칙이 없음
  - vm1에서 `curl -m 3 http://169.254.169.254/latest/meta-data/` → 200
  - vm4 콘솔 로그에 `instance-id` 조회 성공과 `datasource: ec2`가 찍힘
  - `ssh -i ~/cc02-key.pem cirros@10.102.0.172` 키 로그인 성공

## 5. SRE 세 질문

1. **사용자가 무엇을 겪었나:** 새로 만든 VM에 키로 접속할 수 없었다. 기존 VM과 비밀번호 로그인은 멀쩡해서 "내 키 파일 문제"로 오해하기 쉬웠다.
2. **어떤 증상으로 알아챘나:** `Permission denied (publickey)`. IP는 정상(콘솔 로그 `if-info`), ping도 정상(vm1 → vm4)이었다. 콘솔 로그에 `failed to read iid from metadata`, `datasource: None`이 남아 있었다.
3. **운영자가 미리 볼 수 있었던 지표는:**
   - **기존 프로브로는 불가:** 과제지대로 Grafana가 전부 초록인 이유다. 운영진 안내에 따르면 경로 프로브는 FIP·qrouter·VM 사이를 작은 ICMP(`length 128`)로 본다. 메타데이터는 tcp/80이고 VM이 **부팅할 때** 쓰는 길이라, ICMP 프로브가 지나가는 길과 겹치지 않는다.
   - **Black-box 제안:** 네트워크마다 1분 주기로 VM 안에서 `curl -m 3 http://169.254.169.254/latest/meta-data/instance-id`가 200인지 보는 프로브. 기존 프로브가 VM에 SSH로 들어가서 측정하고 있다면, 거기에 한 줄 추가하면 된다.
   - **White-box 제안:** qdhcp 네임스페이스 iptables의 `INPUT` DROP 카운터 증가(Neutron이 만들지 않은 규칙 수 포함), haproxy 메타데이터 요청 수가 0으로 떨어짐, 새 VM 콘솔 로그의 `failed to read iid from metadata`.

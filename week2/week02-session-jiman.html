이론 · Neutron 4장 p.90–102

4장이 답하는 질문 — 인스턴스를 어떻게 네트워크에 꽂나

Neutron의 핵심 기능 하나: 인스턴스에 연결을 주려고 가상·물리 네트워크 인프라를 동적으로 구성하는 것. 인스턴스를 쓰기 전에 스위칭 인프라가 먼저 있어야 한다.

  1. 1tap 인터페이스 — VM의 NIC이 호스트에 어떻게 나타나나
  2. 2브리징 — 인터페이스들을 하나로 묶는 법
  3. 3네트워크 종류 — provider/tenant, local/flat/VLAN/VXLAN
  4. 4LinuxBridge 플러그인 — 브리지로 스위치를 만드는 구조
  5. 5Open vSwitch 소개 — 다음 주로 이어지는 입구

책은 Havana 기준 LinuxBridge·OVS 단독 플러그인을 다룸. 지금은 둘 다 ML2 아래 드라이버로 들어감(부록).

이론 1 p.91

tap 인터페이스 — VM의 NIC이 호스트에 나타나는 모습

  • 인스턴스가 처음 부팅되면 호스트에 가상 NIC이 생긴다 → tap 인터페이스
  • tap 하나 = 게스트 안의 NIC 하나 (1:1)
  • 게스트 eth0으로 보낸 프레임은 호스트의 tap에서 그대로 보인다
  • 이름은 Neutron 포트 UUID에서 따옴 → 호스트를 재부팅해도 이름이 유지
openstack port list --server <이름>-vm2 ID 앞 11자 → tap-<11자>

이름이 포트 UUID 기반이라는 한 줄이, 과제에서 "내 VM의 인터페이스가 뭔지" 찾는 근거였습니다.

이론 2 p.91–93

브리징 — 인터페이스들을 하나의 L2로 묶는다

  • 브리징: 두 개 이상의 L2 네트워크를 연결해 하나의 네트워크로 만드는 일
  • 리눅스 브리지: 여러 네트워크 인터페이스를 연결하는 가상 인터페이스. Neutron에서는 보통 물리 인터페이스 하나 + tap 여러 개
  • 물리 인터페이스는 eth0, 본딩, VLAN 서브인터페이스 모두 가능

브리지에 넣을 때 두 가지

  • promiscuous 모드 — 평소 NIC은 자기 주소가 아닌 프레임을 버린다. 브리지 포트로 쓰려면 남의 프레임도 받아서 넘겨야 하므로 무차별 모드로 바꾼다
  • IP를 주지 않는다 — 브리지에 들어간 물리 인터페이스에 IP가 있으면 그 IP는 접근 불가가 된다

이론 2 p.92 Figure 4.1

Neutron이 쓰는 리눅스 브리지 한 장

VM eth0의 트래픽은 tap, 브리지 인터페이스, 물리 인터페이스 세 군데서 전부 관찰된다. — 책 p.92. 어디에 tcpdump를 걸어야 하는지가 여기 적혀 있었습니다.

이론 3 p.93–95

Neutron의 네트워크 종류

두 범주

  • Provider — 관리자가 만들고, 데이터센터의 물리 네트워크에 직접 대응. 주로 flat·VLAN
  • Tenant — 사용자가 만들고, 기본적으로 다른 네트워크와 완전히 격리

우리: 외부 192.168.200.0/24가 provider, 10.10.10.0/24가 tenant(VXLAN)

네 종류

local같은 노드 안에서만. 다른 호스트의 같은 네트워크 인스턴스와 통신 불가 → 테스트용
flat태깅 없음. 호스트와 같은 네트워크에 있을 수도
VLAN802.1q 태그로 분리. 같은 VLAN = 같은 L2 브로드캐스트 도메인
VXLAN·GRE오버레이. 호스트 간 터널로 캡슐화 (OVS 플러그인)

이론 3 p.94–95 Figure 4.2

오버레이 — 네트워크 위에 네트워크

  • 네트워크를 만들 때 고유 ID를 정하고, 다른 호스트의 같은 네트워크 인스턴스로 가는 트래픽은 그 ID로 캡슐화해 터널로 보낸 뒤 받는 쪽에서 푼다
  • 캡슐화돼 있어서 물리 네트워크 장비는 이 트래픽을 못 읽는다 → Neutron 라우터 없이는 바깥과 격리 (6장, 5회차)

이론 4 p.95–96

LinuxBridge 플러그인 — 세 가지 장치로 스위치를 만든다

커널 모듈 bridge와 8021q에 의존.

tap하이퍼바이저(KVM)가 가상 NIC을 구현한 것. tap으로 보낸 프레임은 게스트 OS가 받는다
VLAN 인터페이스ethX.<vlan> 이름으로 만들면 커널이 802.1q 태그를 붙이고 뗀다. 물리 인터페이스 ethX에 종속
Linux bridge여러 인터페이스를 연결하는 가상 인터페이스

프레임이 VM에서 물리망으로 나갈 때 지나는 장치

  1. tapXXXXVM의 NIC
  2. brqYYYY리눅스 브리지 (네트워크 UUID 기반 이름)
  3. ethX.ZZZVLAN 인터페이스 — VLAN일 때만
  4. ethX물리 인터페이스

3~4개. 이 목록을 외우면 어디를 봐야 하는지 안다.

이론 4 p.96–98 Figure 4.3·4.4

예 ① VLAN — 브리지에 tap들 + VLAN 인터페이스

  • 브리지 이름 brq+네트워크 UUID → 네트워크마다 브리지 하나. VLAN 101이 더 생기면 brqWWWW와 eth1.101이 따로 생긴다
  • brctl show로 이 그림이 그대로 보인다 — bridge id는 VLAN 인터페이스의 부모 NIC(eth1)에서 생성

이론 4 p.98–101 Figure 4.5–4.7

예 ② flat, 예 ③ local — 브리지에 뭐가 꽂혔느냐가 다르다

flat

  • VLAN 인터페이스를 만들지 않고 물리 인터페이스를 브리지에 직접
  • 태깅 없음 → 브리지 하나·물리 인터페이스 하나당 flat 하나
  • flat 두 개면 eth2가 더 필요. 두 브리지 사이는 라우터로만

local

  • VLAN ID도 물리 인터페이스도 못 정함. 에이전트가 브리지를 만들고 tap만 넣는다
  • 같은 브리지의 인스턴스끼리는 통함. 브리지 밖으로는 못 나감
  • 다른 호스트의 같은 네트워크와도 통신 불가 → 테스트용

brctl show # 책 ip link show master <bridge> # 요즘 우분투 (bridge-utils 없음)

이론 5 p.102

Open vSwitch — 브리지와 플로우 규칙으로 포워딩하는 소프트웨어 스위치

커널 모듈

하드웨어 스위치의 ASIC에 해당. 실제 패킷 처리가 일어나는 데이터 플레인

ovs-vswitchd

호스트마다 도는 유저스페이스 데몬. 커널 모듈을 어떻게 프로그래밍할지 지시

OVSDB

호스트마다 있는 로컬 DB. 가상 스위치의 설정을 보관

Neutron은 bridge·openvswitch 커널 모듈과 ovs-vsctl(DB 조작)·ovs-ofctl(플로우 조작)로 OVS를 관리한다.

OVS 구현에서 쓰는 장치 다섯 가지

tap · Linux bridge · veth 케이블 · OVS 브리지 · OVS 패치 포트 — 앞의 둘은 LinuxBridge와 같은 역할. veth는 한쪽 끝에 넣은 프레임이 반대쪽에서 나오는 가상 패치 케이블로, 네임스페이스·브리지 사이를 잇는 데 쓴다.

이론 5 · 미리보기 p.103–104 (3회차 범위)

OVS에서는 왜 Linux bridge가 그대로 남아 있나

  • OVS 브리지는 가상화된 물리 스위치처럼 동작. 포트에 tap·네임스페이스 인터페이스가 붙는다
  • 패치 포트는 OVS 브리지끼리, veth는 OVS 브리지 ↔ Linux bridge를 잇는다
  • 프레임이 VM에서 물리 NIC까지 지나는 장치는 9개: tap → qbr → qvb/qvo → br-int → 패치 포트 → br-ethX → ethX

책이 주는 답

시큐리티 그룹이 켜져 있으면 인스턴스는 br-int에 직접 붙지 않는다. OVS 포트에 붙은 tap에는 iptables 규칙을 걸 수 없어서, tap을 Linux bridge(qbr)에 넣고 그 브리지를 br-int에 교차 연결한다.

그래서 우리 환경에 brq 대신 qbr이 VM마다 하나씩 있다.

이론 · SRE 12장 p.159–160

트러블슈팅은 배우고 가르칠 수 있다

전문가가 된다는 건 시스템이 어떻게 동작해야 하는지 아는 것 이상이다. 왜 동작하지 않는지를 파헤치면서 전문성이 쌓인다. — Brian Redman (책 서두 인용)

  • 자주 하는 사람에겐 몸에 밴 과정이라 설명이 어렵다 — 자전거 타기처럼. 그래도 배울 수 있고 가르칠 수 있다
  • 초보가 막히는 이유: 필요한 두 가지 중 하나가 빠져서
    • 일반적인 방법 — 시스템을 몰라도 쓸 수 있는 절차
    • 시스템 지식 — 어떻게 설계되고 동작해야 하는가
  • 원리만으로도 풀 수는 있지만, 시스템을 아는 쪽이 훨씬 빠르고 정확하다
이게 이 스터디에서 장애보다 책을 먼저 읽는 이유입니다. 4장 = 시스템 지식, 12장 = 일반적인 방법.

SRE 12장 · Theory p.160–161 Figure 12-1

과정 — 가설을 세우고 검증하기를 반복한다

  • 관찰(지표·로그) + 시스템 지식 → 가능한 원인 후보
  • 후보마다 검증 → 아니면 다음 후보 → 근본 원인까지 반복

검증하는 두 방법

  • 관찰된 상태를 가설과 비교해 맞는 증거·틀린 증거 찾기
  • 시스템을 통제된 방식으로 바꿔 반응을 보기 (treat)

SRE 12장 · Common Pitfalls p.161–162

흔한 실수 네 가지

  1. 1증상과 관련 없는 것을 보거나, 지표의 뜻을 오해한다 → 헛다리
  2. 2가설을 안전하게 검증하려면 시스템·입력·환경을 어떻게 바꿔야 하는지 모른다
  3. 3있을 법하지 않은 이론을 세우거나, 지난번 원인에 매달린다 — 전에 그랬으니 이번에도
  4. 4우연의 일치나 공통 원인에서 나온 가짜 상관관계를 쫓는다

1·2는 시스템을 공부하면 줄어든다. 3은 논리 오류 — 모든 장애가 같은 확률은 아니다. 말발굽 소리가 들리면 얼룩말이 아니라 말을 생각하라. 조건이 같다면 단순한 설명을 먼저.

상관관계는 인과가 아니다. 정전이 나면 패킷 손실과 디스크 고장이 동시에 생기지만 서로 원인이 아니다. 지표가 많아질수록 우연히 겹치는 사건도 늘어난다.

SRE 12장 · In Practice p.162–163

실전 ① 문제 보고와 분류

문제 보고

  • 자동 알림일 수도, 동료의 "느린데요"일 수도
  • 좋은 보고 = 기대한 동작 · 실제 동작 · 재현 방법
  • 구글은 메일·채팅으로 온 것도 전부 버그로 연다 → 조사·조치 기록이 남고, 특정인에게 몰리지 않는다

우리 과제 양식의 ②받은 증상이 "실제 동작", 세 질문 ①이 "기대한 동작"

분류 (Triage)

  • 영향 범위에 맞게 대응 — 한 사용자 vs 전체 장애
  • 큰 장애에서 첫 본능은 "원인부터" → 그 본능을 무시하라
  • 먼저 출혈을 멈춘다: 트래픽 우회, 일부 차단, 서브시스템 끄기
  • 조종사의 첫 임무는 비행기를 날리는 것, 고장 진단은 그다음
  • 단, 로그 같은 증거는 보존한다

SRE 12장 · In Practice p.164–166

실전 ② 관찰과 진단

관찰 (Examine)

구성요소 하나하나가 뭘 하고 있는지 볼 수 있어야 한다.

  • 지표 — 시계열 그래프로 어디서 문제가 시작됐는지
  • 로그 — 상세도를 바꿀 수 있게, 필요하면 샘플링, "X에 해당하는 것만" 고르기
  • 현재 상태 노출 — 서버가 최근 요청·설정을 보여주는 엔드포인트

예: 블랙박스 프로브가 5분간 실패 → 알림 → curl로 직접 쳐보니 502 → 헤더의 백엔드 주소로 다음 구간 확인

진단 (Diagnose)

  • 단순화·축소 — 구성요소 사이를 흐르는 데이터를 보고 각 요소가 제대로 변환하는지 확인. 알려진 테스트 데이터를 넣어보기
  • 분할 정복 — 스택 한쪽 끝에서 시작해 다른 끝까지 차례로. 너무 크면 이분법: 반으로 나눠 경계의 통신을 보고, 멀쩡한 쪽을 버린다
  • 무엇·어디·왜 — 고장 난 시스템도 뭔가는 하고 있다. 뭘 하는지, 왜 그러는지, 자원·출력이 어디로 가는지

장애 · 이론을 우리 환경에 얹으면

vm2는 이렇게 꽂혀 있다

4장에서 본 그대로입니다. tap(VM의 NIC) → Linux bridge(SG를 걸기 위한 qbr) → veth(한쪽에 넣으면 반대쪽으로 나오는 케이블) → OVS 브리지(br-int). 이번 주 장애는 이 그림 안에서 났습니다.

장애 · 정답

A는 qbr에 qvb가 없었고, B는 br-int에 qvo가 없었다

Aqbr에 꽂혀 있어야 할 qvb가 빠짐 ip link show master qbr-<id> 정상 → tap-<id>, qvb-<id> 장애 → tap-<id> 만

4장 "local" 그림과 같은 상태 — tap만 꽂힌 브리지는 호스트 밖으로 못 나간다

Bbr-int에 꽂혀 있어야 할 qvo가 빠짐 ovs-vsctl list-ports br-int | grep <id> 정상 → qvo-<id> 장애 → (없음)

veth까지는 이어져 있지만 OVS 스위치 포트가 없다

둘 다 결과는 같다 — vm2 ping·SSH 불가, vm1은 정상. 미끼였던 SG의 ICMP 누락은 ping만 설명하고 SSH 불가는 설명하지 못한다 (흔한 실수 1번).

SRE 세 질문 — 2회차 답

  1. 사용자vm2에 접속이 안 된다. 기대한 동작은 "접속된다", 실제는 "안 된다". qbr도 veth도 사용자는 모른다
  2. 증상FIP로 ping·SSH 모두 실패, vm1은 정상. 12장 Shakespeare 예와 같은 모양 — 블랙박스 프로브 실패가 첫 신호
  3. 지표blackbox_exporter의 ICMP·SSH probe가 동시에 down. 포트 하나가 아니라 경로 전체가 끊겼다는 신호

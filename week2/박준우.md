# 2회차 제출 — 박준우

> 계정: `cc02` · 작성일: 2026-11-02

**결론:** cmp02의 OVS 통합 브리지 `br-int`에서 vm2 포트의 veth 끝 `qvo4a06126b-09`가 빠져 있다. 장치(tap·qbr·qvb·qvo)는 전부 살아 있는데 br-int와의 연결만 없어서, vm2가 L2에서 통째로 고립됐다.

```
net01: [qrouter] qg-(FIP DNAT ✓) → qr- 10.102.0.1 (ARP 응답 없음) → br-int → br-tun ═VXLAN═╗
cmp02: vm2 ← tap ✓ ← qbr ✓ ← qvb ✓ ═ qvo ✓   ✂   br-int (qvo 포트 없음) ← br-tun ←══════╝
```

## 1. 읽기 핵심 (한 장)

- ML2/OVS + iptables 하이브리드 방화벽에서 VM 패킷은 컴퓨트 노드 안에서 `VM eth0 → tap → qbr → qvb ═ qvo → br-int → br-tun` 순서로 지난다. VM과 br-int 사이에 장치 4개, 연결 4군데(tap↔qbr, qbr↔qvb, qvb↔qvo, qvo↔br-int)가 있고 하나만 끊겨도 VM은 고립된다. 이번에 끊긴 곳이 마지막 **qvo↔br-int**였다.
- 접두어: `tap` = 하이퍼바이저 쪽 가상 NIC, `q` = Neutron의 옛 이름 Quantum. `qbr` = 포트마다 하나씩 만드는 Linux bridge, `qvb`/`qvo` = 그 브리지와 OVS를 잇는 veth 쌍의 bridge 쪽/OVS 쪽 끝. 라우터 쪽은 `qr-`(내부 GW), `qg-`(외부 GW).
- qbr이 따로 있는 이유는 OVS 포트에 iptables를 걸 수 없어서 시큐리티 그룹을 적용할 Linux bridge를 끼운 것. 즉 **SG 필터링은 qbr에서**, **L2 스위칭은 br-int에서** 일어난다. 둘을 구분하니 "SG냐, 배선이냐"를 따로 검증할 수 있었다.
- 장치 이름이 `접두어 + 포트 ID 앞 11자`라서 `openstack port list`의 포트 ID(`4a06126b-0934-…`)만으로 cmp02에서 `tap/qbr/qvb/qvo4a06126b-09`를 바로 찾았다. API 계층과 데이터 계층을 잇는 열쇠.
- Horizon의 ACTIVE는 nova가 보는 VM 상태이지 tap 뒤 배선 상태가 아니다. 실제로 vm2는 ACTIVE인데 Neutron 포트는 DOWN이었다.
- SRE 12장: 가장 그럴듯한 원인부터 *고치면* ① 시스템이 바뀌어 증거가 사라지고 ② 우연히 나아져도 진짜 원인을 모르며 ③ 안 나아지면 변수만 늘어난다. 공용 노드에서는 남의 환경까지 건드린다. 그래서 상태를 바꾸지 않는 관찰(조회·tcpdump·네임스페이스 ping)로만 가설을 하나씩 기각했다.
- 적용: "ping·SSH 둘 다 불통"이면 SG가 제일 그럴듯해 보이지만, ping(ICMP)과 SSH(TCP 22)는 서로 다른 규칙이고 SG는 ARP를 막지 않는다. "라우터가 vm2의 ARP조차 못 받는다"는 관찰 하나로 SG 가설을 확실히 버릴 수 있었다.

## 4. 원인 · 복구 방안

복구는 **실행하지 않았다.** 어떻게 고치면 될지만 적는다.

- **원인 (한 문장):** cmp02의 OVS 통합 브리지 `br-int`에서 vm2 포트의 `qvo4a06126b-09`가 빠져 있어서(veth 장치 자체는 UP), vm2의 tap→qbr→qvb→qvo 구간이 br-int와 단절됐다.
- **끊긴 지점이 이 증상으로 보인 이유:**
  - L2가 끊겨 **ARP부터 실패**한다. 라우터(qr- 10.102.0.1)가 vm2의 IPv4 주소에 대한 MAC을 몰라 ICMP든 TCP든 프레임 자체를 내보내지 못한다 → **ping·SSH가 프로토콜과 무관하게 동시에 불통.** SG였다면 규칙이 프로토콜별이라 둘이 따로 놀았을 것이고, ARP는 통과했을 것이다.
  - ARP가 실패하면 라우터가 `ICMP Host Unreachable`을 돌려주기 때문에 SSH는 timeout이 아니라 **`No route to host`로 즉시** 실패했다.
  - VM 프로세스는 멀쩡하므로 nova/Horizon은 **ACTIVE**. qvo가 br-int에서 사라지자 OVS 에이전트가 포트를 장치 삭제로 보고 Neutron 포트를 **DOWN**으로 보고한 것으로 추정 (포트 마지막 변경 10/27 05:16:45Z, revision이 vm1보다 하나 많음).
  - 참고로 vm1처럼 vm2 MAC을 캐시에 갖고 있는 쪽도 ping이 실패했다. MAC을 알아도 cmp02 br-int에 그 MAC으로 가는 포트가 없어서 프레임이 버려지기 때문이다.
- **복구하려면 (명령 또는 절차):**
  1. (최소 변경, VM 재시작 없음) cmp02에서 qvo를 원래 포트 정보와 함께 br-int에 다시 붙인다. VLAN tag는 수동으로 넣지 않고 에이전트가 붙이게 둔다.
     ```bash
     sudo docker exec openvswitch_vswitchd ovs-vsctl --may-exist add-port br-int qvo4a06126b-09 \
       -- set Interface qvo4a06126b-09 \
          external_ids:iface-id=4a06126b-0934-452d-b8bd-6a6f3ce20e63 \
          external_ids:iface-status=active \
          external_ids:attached-mac=fa:16:3e:cc:5f:5e \
          external_ids:vm-uuid=28d68e38-6def-41ab-bea5-728263f2d1f8
     ```
     `iface-id`를 보고 neutron-openvswitch-agent가 새 포트를 인식해 local VLAN tag와 flow를 설치하고 포트를 ACTIVE로 올린다.
  2. (대안) `openstack server reboot --hard cc02-vm2` — nova(os-vif)가 VIF를 처음부터 다시 꽂는다. 확실하지만 VM이 재부팅된다.
- **복구 후 무엇으로 확인하면 되는지:**
  - cmp02: `ovs-vsctl show`에 `qvo4a06126b-09`가 br-int 아래 `tag: N`(4095 아님)으로 보임
  - ops01: `openstack port show 4a06126b-… -c status` → `ACTIVE`
  - net01: `ip netns exec qrouter-9474df2d-… ip neigh show 10.102.0.247` → `REACHABLE`, `ping 203.0.113.201` 응답
  - ops01: vm2 SSH 접속 성공, Grafana vm2 FIP 프로브가 정상으로 복귀

## 5. SRE 세 질문

1. **사용자가 무엇을 겪었나:** 어제까지 되던 vm2에 SSH·ping이 전혀 닿지 않았다. 같은 방법으로 vm1은 되므로 계정·키·클라이언트 문제가 아니다.
2. **어떤 증상으로 알아챘나:** SSH가 `No route to host`로 즉시 실패, ping은 `Destination Host Unreachable`. 그런데 Horizon/`server list`에서는 ACTIVE라서 콘솔만 봐서는 이상이 보이지 않았다.
3. **운영자가 미리 볼 수 있었던 지표는:**
   - **Neutron 포트 상태:** VM은 ACTIVE인데 그 VM의 포트가 `DOWN`인 불일치. 포트 마지막 변경 시각(10/27 14:16 KST)으로 보아 그때부터 API로 보였을 것으로 추정한다. "ACTIVE VM의 DOWN 포트 수"는 바로 경보로 걸 수 있는 지표다.
   - **tap 인터페이스 카운터:** 호스트→VM 방향(tap TX)이 VM→호스트(RX)에 비해 적다 (vm2 RX 9,617 / TX 436, vm1 RX 719 / TX 1,735, 한 시점 비교). 시간에 따라 TX가 늘지 않는지 추적하면 더 확실한 지표가 된다.
   - **Grafana vm2 FIP 프로브:** 장애 시각과 맞춰 볼 예정이었으나 이번 제출 시점에는 Grafana 로그인을 못 해서 확인하지 못했다.

## 6. 한 줄 회고 (선택)

- "ACTIVE인데 안 된다"는 말은 컨트롤 플레인과 데이터 플레인이 어긋났다는 뜻이다. API의 포트 상태(DOWN) → 노드의 장치(qvo) → 실제 패킷(tcpdump) 순서로 계층을 내려가니 고치지 않고도 원인 한 군데를 특정할 수 있었다.
